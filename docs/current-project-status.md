- **A run that defers a domain is reported as `status: 'completed_with_deferred'`, never `'reconciled'`.** These are not the same thing, and calling code must inspect `status` (or `deferredDomains.length`), not just `ok`, to tell them apart — `ok` is `true` for both, by design (deferring is a deliberate, acknowledged choice, not a failure). This mechanism itself is untouched by §0 — it still exists for any future domain an operator explicitly chooses to defer; `payments` simply has no remaining reason to.
- **Crash/resume safety** has been proven via deliberate fault injection at each real kill-window (mid-write, between a target write and its ledger acknowledgement, between GoTrue account creation and ledger linkage, mid-transaction for subscriptions/relationships/the migration-seed admin identity) — every window closes to either "fully committed" or "fully rolled back," never a silently-orphaned partial write, across seven rounds of adversarial review.
- **Strict CLI parsing, immutable approval artifacts, and bidirectional ledger integrity** (every target row traces to a ledger entry AND every ledger entry's claimed target still exists) are enforced structurally in the production orchestrator, not by convention.

§0's rehearsal DID exercise this tooling against a real, read-only backup of real production Mongo data (56 real documents) — still never against the real Supabase project or real deployment credentials, which remain untouched.

## 5. Booking-First Enrollment (no in-app online payment)

Separately from the Mongo→Supabase migration effort above, the product itself changed how students subscribe: **choose a plan → submit a booking request → contact over WhatsApp → pay off-site → admin manually activates the subscription.** There is no in-app checkout, no card entry, and no client-side Stripe/PayPal/Paymob call anywhere in the frontend any more — and, as of the hardening pass below, no *server-side* path to one either.

- The frontend's `CheckoutModal` and the `/payment/success` · `/payment/cancel` capture flow it fed into are gone; those two routes now show a clear "online payment is no longer used here" notice and a link back into the booking flow instead of 404ing for anyone with an old link.
- Booking requests reuse the existing `Enrollment` model/API (`POST /api/enrollments`, admin CRUD at `/api/v1/admin/enrollments`) rather than a new resource — it already collected everything a booking request needs. It gained a unique `bookingRef`, shown to the student and embedded in a pre-filled WhatsApp message, plus admin-only bookkeeping fields (`agreedAmount`, `currency`, `paymentMethodExternal`, `paidAt`, `renewalAt`, `adminNote`) and two extra status values (`awaiting_payment`, `paid`) alongside the pre-existing ones — additive, so no data migration was needed.
- This is administrative bookkeeping only, never a payment gateway: no card, bank, or account credential is collected or stored anywhere in this flow.
- **The payments domain itself (Stripe/PayPal/manual-payment controllers, routes, models, and all historical `Payment`/`Invoice`/`ManualPayment` records) is untouched and still legacy/deferred** — nothing here changes its status in the Mongo→Supabase migration described above; the admin manual-payment review tab still works for any historically-submitted record.

### 5a. Server-side hardening (closes the "frontend-only removal" gap)

A review of the initial booking-flow branch found the payment shutdown was UI-only — every gateway route was still live and reachable directly. Closed as follows:

- **Every customer-reachable payment/checkout route now returns `410` with a stable `{ error: 'PAYMENTS_DISABLED' }` body**, not just an unlinked frontend page: `POST /api/payments/stripe`, `POST /api/payments/paypal`, `POST /api/payments/paypal/:orderId/capture`, `GET /api/payments/manual-methods`, `POST /api/payments/manual`, `POST /api/coupons/validate` (`backend/middleware/paymentsDisabled.js`, wired in `backend/routes/paymentRoutes.js` / `couponRoutes.js`). The Stripe/PayPal webhooks (`/stripe/webhook`, `/paypal/webhook`) stay live and untouched — server-to-server, never customer-triggered, still needed for any in-flight/historical transaction. The gateway controllers themselves are untouched in `controllers/` (legacy/deferred), just no longer routed to from a customer request.
- **Mass-assignment fixed** on the public `POST /api/enrollments`: it used to spread the entire request body into `Enrollment.create()`. It now reads only an explicit allowlist of customer-facing fields (`backend/utils/enrollmentValidation.js`'s `pickPublicBookingFields`); `status` is always forced server-side to `'pending'`, and `bookingRef`/`agreedAmount`/`currency`/`paymentMethodExternal`/`paidAt`/`renewalAt`/`adminNote` are structurally unreachable from a guest request (Mongo) or not even parameters of the guest-facing RPC (Supabase — see below).
- **WhatsApp is now required and validated**, both client-side (`Enroll.jsx`) and server-side (`normalizeWhatsapp()` — E.164-ish, 7–15 digits after separators are stripped), since it is the only contact channel this flow uses to arrange payment.
- **`bookingRef` generation uses `node:crypto`'s `randomBytes`**, not `Math.random()` (a booking reference is shown to strangers and used as a lookup key), with the same retry-on-collision behavior as before; the Supabase equivalent (`submit_enrollment_booking()`, see below) uses `gen_random_uuid()` the same way. The frontend's booking-confirmation button disables itself and its own submit handler no-ops while a request is in flight, so a double-click cannot create two booking requests.
- **Admin `PUT /api/v1/admin/enrollments/:id` replaced its generic `Object.assign(doc, req.body)` with an explicit allowlist + validation** (`buildAdminUpdatePatch()` in the same shared util, used by both backends): `status` must be one of the 6 real values; marking a booking `enrolled` requires an `agreedAmount` already on record or being set in the same request; `agreedAmount` must be `>= 0`; `currency` must be a 3-letter ISO code; `paidAt`/`renewalAt` must be valid dates; a field sent as explicit `null` clears it, distinct from a field simply omitted. Financial fields (`agreedAmount`/`currency`/`paymentMethodExternal`/`paidAt`/`renewalAt`) additionally require the `payments:write` permission on top of the base `enrollments:write` — `editor` was widened to hold `enrollments:write` (so it can run the day-to-day booking-status pipeline) but still lacks `payments:write`, so it cannot touch the money fields; only `admin`/`super-admin` can.
- **Mongo/Supabase parity for the new fields**: `lib/db/drizzle/0025_booking_first_enrollment.sql` adds the same 7 columns to the Postgres `enrollments` table, widens its own status `CHECK` allowlist, adds the `editor`→`enrollments:write` `role_permissions` row, and adds a `submit_enrollment_booking()` `SECURITY DEFINER` RPC — the guest-facing Supabase path no longer does a raw column-restricted `INSERT` (which couldn't return the generated `bookingRef` at all, since anon/authenticated have no `SELECT` grant on `enrollments`); it calls this RPC instead, which enforces the same name/email/whatsapp-required rules as the Mongo controller and returns only the generated `bookingRef`, never a row. `backend/data/supabase/enrollmentController.js` and `data/supabase/admin/enrollmentsAdminController.js` were updated to match. `backend/scripts/migration/mongo-to-supabase.mjs`'s `enrollments` domain transform/upsert now carries all 7 new fields and both new status values through a real Mongo→Postgres migration instead of silently dropping them.
- Test coverage added across both backends: `backend/tests/enrollment-booking.test.js` + `enrollment-booking-validation.test.js` (mass-assignment, WhatsApp requirement/normalization, collision retry, admin validation, the financial-permission boundary), `backend/tests/payment-checkout.test.js` (every disabled route returns 410 and has no side effect; webhooks stay live), `lib/db/test/rls.local.test.mjs` + `acl.local.test.mjs` (the `submit_enrollment_booking()` RPC, and that none of the 7 new columns are guest-INSERT-able), and `backend/scripts/migration/lib/enrollments-transform.test.mjs` (the lossless field-mapping, in isolation).
